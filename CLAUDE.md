## Architecture

Two apps: `backend/` (Django REST API) and `frontend/` (Vue 3 SPA), talking over plain HTTP. `docker compose up --build --renew-anon-volumes` runs the whole stack (Postgres 17 + backend :8000 + frontend :5173) — `-V` because the SPA's `node_modules` is an anonymous volume Compose otherwise carries over a rebuild, and the backend image is built with `requirements-dev.txt` here because `DEBUG` installs the toolbar (TD-51). Bare-metal: backend falls back to SQLite, frontend defaults its API base URL to `http://127.0.0.1:8000` (`VITE_API_BASE_URL` to override); both servers must run for the app to work end to end.

Configuration is env-driven with dev-safe defaults — see `.env.example` (root, used by compose) and `frontend/.env.example`. `backend/backend/settings.py` reads `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, CORS/CSRF origins, `WEBSITE_URL`, `FRONTEND_URL` (C1 — the SPA's own base URL, used to build invite/password-reset links; distinct from `WEBSITE_URL`, which is the API's), and switches to Postgres when `POSTGRES_HOST` is set. **`MAILERS`** (not `EMAIL_BACKEND` — migrated 2026-08-30 for TD-34, since Django 6.1 deprecates the whole `EMAIL_*` family and 7.0 removes it) follows the same `TESTING`/`DEBUG` gating as everything else: `locmem` under pytest, the console backend in dev, real SMTP otherwise. The environment variables keep their names (`EMAIL_HOST`/`EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD`/`EMAIL_USE_TLS`) and are read into the mailer's `OPTIONS`; **do not reintroduce any `EMAIL_*` Django setting** — with `MAILERS` defined, Django raises on one rather than ignoring it. **A mail server that does not answer is handled, not fatal** (TD-38/39, 2026-09-10): the admin's approve action is one `transaction.atomic()` with its send and rolls back with a message to the author, and password reset answers 200 for every address even when the send fails — a 500 there was an enumeration oracle. **Production has a `LOGGING` block** (TD-40): errors to stderr, `django.request` held at ERROR, because Django's default sends a production traceback only to `ADMINS` by e-mail, which here meant nowhere. Outside dev and tests, `CACHES` is the **database cache** so the credential rate limits (TD-18) are counted once rather than once per gunicorn worker; it needs `manage.py createcachetable` at release time.

### Backend (`backend/`)

Django 6 + DRF, thirteen apps:

- `account` — custom `User` (UUID pk, email login, no username; `role` = `citizen`|`admin`, default citizen, promoted via Django admin per spec F1.3; the internal `citizen` identifier is unchanged even though the v2 spec calls this tier "Collaborator" — a vocabulary shift, not a rename). `AUTH_USER_MODEL = 'account.User'`. **C1 (spec accounts.md):** there is no public signup — `POST /api/users/collaborate/` (public, honeypot + timing anti-spam, no CAPTCHA) files a `CollaborationRequest`; a `CollaborationRequestAdmin` action in Django admin approves or rejects it (approving creates the `User` with `set_unusable_password()` and e-mails a single-use invite link) or rejects it. `AccountToken` is one model shared by invite and reset (`purpose`, hashed token, `expires_at`, `used_at`; `AccountToken.create_for()` retires any prior unused token of the same purpose) — `POST /api/users/acceptinvite/` and `POST /api/users/requestpasswordreset/` + `/api/users/confirmpasswordreset/` consume it (reset requests always return 200, existing e-mail or not, to avoid enumeration). `User.is_steering` (spec politics.md) is a confidential capability flag, admin-settable only via `UserAdmin` — it must never be added to `UserSerializer`/`MeSerializer`. Its one consumer is C5's seggi overlay, read through `maps`' visibility gate ([ADR-0006](docs/adr/0006-overlay-visibility-gate.md)) — never through a serialized field.
- `content` — **C2 (spec content.md, ADR-0004):** the shared core every card type wraps, not an API of its own (a library app, like `common/` but with models) — **save one endpoint since 2026-10-23**: `GET /api/content/counts/` (review PR-9), each type's published count for the Schede menu, with the types *found* from `Card`'s one-to-one rows (`content/api.py::type_keys`) rather than listed. `Card` (UUID pk, `title`, `body_html` — always pre-sanitized, `author` FK `PROTECT`, `is_published`, plus `language`/`translation_of`, wired up in **C4**) has no type-discriminator field — a card's type is found via the reverse OneToOne (`hasattr(card, 'feste')`), not a stored field that could drift out of sync. `CardImage` (ordered, `common/images.py` unchanged) and `MapFeature` (`kind` = `point`|`route`, `position`, optional `label` — consecutive `route` rows form a polyline; `point` rows are independent pins) cover every type's map footprint in the spec's table without a schema change per type. `content/sanitize.py::sanitize_html` (`nh3`, strict allowlist, h2/h3 only — a card's own title is the page's h1) is the **one chokepoint** every type's write path calls; its plain-text counterpart is `content/fields.py::PlainTextField`, which the type serializers use for `ingredients`/`procedure`/`programme`/`meaning` and friends so a `<textarea>`'s browser-normalised CRLF does not become what the archive stores (TD-36); see the ADR-0001 amendment for why this is safe to render via `v-html`. **C3** added `content/api_helpers.py` (image save/remove, point-pin parse/replace, author-or-admin permission checks — `replace_points` is a **diff by id** since TD-50: every type's read side returns each pin's `id`, the form sends it back, and a pin sent with its id keeps its row, which is what keeps a tour stop on it) and `content/serializers.py` (the shared `CardImageSerializer`) — extracted once a second type app needed the same write-path logic feste had inlined, so every type app (feste included, for images) now shares one implementation rather than one copy each. **C4 (spec translations.md):** `content/api_helpers.py::start_translation` is the single write path every type's new `<type>_translate` view calls — it forbids translating a translation (no chaining: the group is always original-plus-its-translations, never a tree) and creates the empty target-language `Card` + blank type row T2 describes ("traduci questo articolo in…" opens an empty version alongside the source), English (`en`) being the only entry in `TRANSLATABLE_LANGUAGES` so far (T1/T3 — more languages and machine-translation assistance are later work). **Three decisions of 2026-09-09 (spec translations.md T5/T6/T7) live in the same two files.** `content/serializers.py::media_source` returns the card that owns a group's photographs and map features — the original, whichever member you hold — and every type's Read serializer resolves `images`/`pins`/`route` through it, so a translation *shows* the original's and owns none; `content/api_helpers.py::reject_media_on_translation` is the write half, one guard behind `save_images`/`remove_images`/`replace_points` and feste's route, refusing loudly rather than dropping an upload. Every type's **public list** filters `card__translation_of__isnull=True` (one thing in the world, one row — the rule C5's map already followed) while **`mine/` deliberately does not**, since it is a collaborator's only way back to an unfinished translation. **T8 (2026-09-19): a translation is public only with its original** — publishing one before its original is refused (`require_original_published`, every type), and unpublishing or deleting the original takes its translations down (`Card.save()` and a `pre_delete` receiver in `content/models.py`, so Django admin obeys it too); republishing the original does not bring them back. And every Read serializer carries **`original_title`** — the Italian name, which is the heading of a translated card too, with the translation's own `title` shown under it as a subtitle: the signs in Gaeta are in Italian, so a fully translated title is how a tourist fails to find the place. `CardArticle.vue` renders that pair and marks `lang` on the article and `lang="it"` on the heading (WCAG 3.1.2, inside ADR-0005's bar). `content/serializers.py::visible_translations` is the matching read-side helper — published-only for anyone but the card group's author/admin — that every type's Read serializer calls for its `translations` field (a `TranslationSerializer` list) alongside plain `language`/`translation_of` fields. **What is known about getting in is `content.Availability`** (ADR-0008, built 2026-10-13): one row per card, only on `content.models.ACCESS_TYPES` (chiese, luoghi), owned by the original and read through `content/serializers.py::availability_of` — which answers a card with no row exactly like an empty one, `state: 'unknown'`, so *no row* can never read as *open*. `hours` is free text; `hours_updated` is set by `Availability.save()` whenever the hours change, in Gaeta's date (`today_in_gaeta`, `Europe/Rome` — `TIME_ZONE` is UTC), never by a form. It travels as an `availability` JSON object beside the multipart form (`parse_availability`/`save_availability` in `api_helpers.py`, refused on a translation); the reader sees it through `components/content/VisitInfo.vue`, which shows nothing when nothing is known and never the hours without their date. `content/test_availability.py`'s tests are named after the mistakes they guard against.
- `feste` — **C2, the first (and richest) thin type app**, proving the core per ADR-0004's "days not weeks" bar: `Feste` (`card` OneToOneField as `primary_key=True` — a Feste's id **is** its card's id, the classic Django one-to-one-as-subtype pattern), `recurrence` (free text, e.g. "Ogni 9 giugno" — not a computed calendar rule), `programme` (plain text, not rich). `FesteWriteSerializer` is a plain `Serializer`, not a `ModelSerializer`: it writes across `Card`+`Feste` at once, and images/route are handled in `feste/api.py` (`request.FILES.getlist('images')`, a JSON-encoded `route` string) rather than fought into DRF's multipart+nested-list handling. `GET /api/feste/mine/` exists because collaborators are not Django-admin `is_staff` (C1) — it's the only way they find their own drafts again. A draft 404s (not 403s) for anyone but its author/admin, so an outsider can't distinguish "doesn't exist" from "exists but hidden".
- `chiese`, `ricette`, `personaggi`, `dialetto` — **C3, the remaining four thin type apps**, each following feste's shape (models/serializers/api/urls/admin/migrations/tests) but calling `content/api_helpers.py` instead of re-implementing it: `Chiesa` (one extra field since 2026-10-13, `from_outside` — «Se la trovi chiusa», cosa-fare.md D7, written per language; map footprint is one fixed pin, so its write path caps the shared point-parsing at `max_points=1` rather than a bespoke scalar field), `Ricetta` (`ingredients`/`servings`/`procedure`, all plain text; zero-or-more "sold here" pins), `Personaggio` (`life_dates` as free text — same rationale as `recurrence`, historical dates are often uncertain, e.g. "sec. XV" — plus a small-capped optional pins list for birthplace/monument), `dialetto`'s `Termine` (`meaning`/`example_usage` — **no `term`**, dropped 2026-09-09 because the card's title is the word and a reader saw it twice on every entry; **no map handling at all** — its `api.py` never imports the point helpers, matching the spec's "none" footprint for this type). Mounted at `/api/chiese/`, `/api/ricette/`, `/api/personaggi/`, `/api/dialetto/`.
- `libri` — **the sixth type (2026-09-09), and the first one nobody had planned for**: recommended books about Gaeta, proposed and specified the same morning (spec content.md), built the same day. `Libro` carries `book_author`/`year`/`publisher`, all free text — **`book_author`, never `author`**, because `Card.author` is the collaborator who wrote the card and a model holding both under near-identical names is how the two get confused. Its shape is copied from `dialetto` rather than from chiese: **no map handling at all** (a book is not a place; the library is, but that card would be about the library — and C5's rule means a sixth map layer would owe a sixth list too). Mounted at `/api/libri/`. **Covers are the publisher's or none, never a scan** (2026-09-09) — a rights rule no code can enforce, so it rides on the images field's own hint via `typeConfigs.ts`'s `imagesHint`, attached to the input rather than floating beside it. A second type proposed in the same conversation, `tradizioni`, was **dropped by the author within the hour** — every card he could name for it was already a festa or a ricetta; the reasoning is kept in the spec because it is the argument against the next generic type too.
- `luoghi` — **the seventh type (built 2026-09-18, spec content.md)**: the places a visitor goes that are not churches — beaches, the castle, monuments, museums, viewpoints, walks. `Luogo` is chiese's shape (one fixed pin, `max_points=1`) plus `genre` and `how_to_get_there` (plain text). **`Genre` is an admin-managed model**, like `reports.Category`, seeded by `luoghi/migrations/0002_seed_genres.py` from Google Maps' place taxonomy and addressed by **slug** everywhere (`/api/luoghi/?genere=spiaggia`, `/luoghi?genere=spiaggia`); `GET /api/luoghi/generi/` lists them with a published-count, and restates `order_by` because Django drops `Meta.ordering` from an aggregating query. **Churches are not a genre** — they stay their own type, and the reader meets them beside the genres (a *Chiese* chip on `/luoghi`). A translation shows its original's genre, as it shows its original's pin. On the frontend it is a `typeConfigs.ts` entry like the others, which added two generic capabilities: a `select` field kind whose options come from an endpoint (`optionsEndpoint`, rows of `{slug, name}`, shown through `displayKey`), and a `listFilter` that `TypeListView` reads from the URL query. Mounted at `/api/luoghi/`.
- `itinerari` — **the eighth type (backend built 2026-09-18, spec itinerari.md)**: curated tours. `Itinerario` (card + `form` `raccolta`|`percorso` + free-text `duration` + `intents` M2M) with ordered `Stop` rows (a **card that has a place** — never a translation — an optional chosen pin, a plain-text `note`). **A stop names its pin, not a position** (TD-50, 2026-10-12): `Stop.point` is a FK to the `MapFeature`, `SET_NULL` so a deleted pin falls back to the card's first; the API still speaks `point_index`, resolved to the pin on write and recomputed on read, because that is what the form's select holds; `Intent` is admin-managed and seeded (`mare`, `mangiare`, `citta`), listed with published-counts at `/api/itinerari/intenti/`. Stops/intents/path arrive as JSON strings beside the multipart images. **I4 and the stop rules live in `itinerari/rules.py`** (since TD-49, 2026-10-12 — `api.py` before), so both write paths apply them: the API, and Django admin's stop inline (`StopInlineFormSet`) plus the generic card form, where a tour's `is_published` is edited. That last one is in `content`, which must not know its types (ADR-0004), so `content/publishing.py` is a **registry of publish checks**: `CardAdmin`'s form runs every registered check, `content` registers T8's original-first itself, and `itinerari`'s `AppConfig.ready()` registers I4 — a type with a publish rule of its own registers it there. Publishing is refused while a stop's card is a draft, and the read serializer drops stops whose card was unpublished later for readers (the author/admin see them flagged). The walked path is the itinerary card's own `route` MapFeatures; a raccolta has none. A translation shows the original's stops, path, form and intents. **Not a map layer** — `maps.CARD_TYPES` is the list of types that *can be stops*, and itinerari is not in it. Mounted at `/api/itinerari/`. **Frontend built the same day:** `/benvenuto` (`WelcomeView`, the one address printed on B&B cards — never rename it), `/itinerari` (the generic `TypeListView` with `itinerarioConfig`, intents as filter chips), `/itinerari/:id` (`ItineraryDetailView`: the article with its stops, and the guided mode at `?tappa=N` — position in the URL, *Come arrivarci* from `lib/directions.ts::directionsUrl`, which every card with a place uses too since review PR-3), `/itinerari/nuovo` and edit-in-place through `components/content/ItineraryForm.vue`. Stops are picked on the map through `components/forms/StopsField.vue`, which lends `stores/map.ts` an editor of kind **`stops`** — the one kind whose clicks land on *cards' pins* (`editorPick`) rather than on the ground, and which does not dim the other cards. Itinerari sits in `AppHeader`'s pill between Esplora and Il progetto (with *Cosa fare* after it since 2026-10-13); `seed_e2e` seeds "Itinerario E2E" for `itinerari.cy.ts`.
- `maps` — **C5 (spec map.md, ADR-0006):** the map's own app, mounted at `/api/map/`. Two public endpoints: `features/` returns every **published, non-translated** card that has a `MapFeature`, grouped one entry per card (`{id, type, title, points, route}`) so the SPA draws all five card layers (luoghi since 2026-09-18) from one unpaginated call — translations are excluded because a translated card is a second `Card` row and would put two pins on one doorstep. `overlays/` returns what *this reader* may see. `Overlay` is one model for both kinds the spec asks for (`kind` = `vector`, a GeoJSON document, or `raster`, a georeferenced image plus its `south`/`west`/`north`/`east` bounds), validated in `clean()` because the write path is Django admin — there is no collaborator-facing overlay editor, the author supplies the boundaries and the scans. **The gate:** `Overlay.objects.visible_to(user)` is the only place `visibility` (`public`|`collaborators`|`steering`) is read, it defaults to **`steering`** (the most restrictive tier — publishing an overlay is one explicit admin edit, never a side effect of creating one), and `OverlaySerializer` **must never serialize it** — a test asserts the word never appears in a response body. This is `User.is_steering`'s first consumer; read ADR-0006 before touching any of it. **`maps.Zona` (2026-10-13, spec cosa-fare.md Part −1 D2) is the editorial zones** — *not* official boundaries (none is published; the page says so): admin-managed GeoJSON outlines: six hand-drawn drafts seeded by `maps/migrations/0005_seed_zones.py`, **redrawn on OpenStreetMap by `0006_zones_redrawn_on_osm.py` (2026-10-14)** — cut on the comune's coastline with a ~40 m sea margin, no overlaps, plus Ariana and Arenauta — which touches a zone only while it still holds 0005's draft, so the author's admin corrections survive; the outlines are ODbL-derived (attribution in the migration). A card is in a zone **by position, never by choice** (`maps/zones.py`, pure-Python point in polygon): a place by its pin, a festa where its procession stops, a percorso where it starts, a raccolta wherever any published stop is. `/api/map/features/` carries each card's `zones` (plus a luogo's `genre` and a known access `state` — never the hours), itineraries carry `zones`, chiese and luoghi carry theirs named — `{slug, name}`, for the card's *Dove si trova* (review PR-3, content.md), and feste too since 2026-10-23, for the panel's eyebrow (review PR-23), while itineraries keep their slugs — and `GET /api/map/zone/` lists the zones with a count of published chiese and luoghi. **Since 2026-10-15 (spec map.md M5) `features/` also returns the drafts its reader may already read** — their own, every one for an admin, nobody else's — each entry carrying `is_published`; `GaetaMap` draws them hollow and dashed, `PlacesList`/«Cosa si può fare qui»/`StopsField` say *bozza*, `MapStage` refetches on sign-in and sign-out, and **every public count (zones, genres, intents, `/benvenuto`) stays a count of published cards** — a test asserts a draft never moves a zone's count, not even for its author.
- `reports` — the core domain: `Category` (admin-managed, seeded with 7 Gaeta defaults in a data migration), `IssueReport` (status workflow `open→acknowledged→resolved`, `rejected`; transitions in `ALLOWED_TRANSITIONS`, admin-only via `role`), `Upvote` (unique user+report, denormalized `upvotes_count`). Photo uploads go through `common/images.py` — a plain package, not an app — shared with `account` (and now `content`) so every upload gets the same treatment (TD-12): ≤5MB, JPEG/PNG/WEBP **by decoded content**, a 40 Mpx header check before `load()`, EXIF stripped after the orientation is applied, and the stored filename's extension rebuilt from the detected format (TD-13 — Django's own `validate_image_file_extension` allows 70 extensions, many of which are not `image/*`). List/detail/map/categories were **public** until 2026-10-22; **since then every reports endpoint, categories included, answers only to an account** (spec reports-and-polls.md R1, pinned by `test_anonymous_cannot_read_reports`) — nothing in `reports/api.py` opts out of the global `IsAuthenticated`, and nothing should.
- `polls` — spec §7 rebuild (M3): `Poll` (question ≤200, `closes_at?`, manual `is_closed`; *effectively* closed when either applies — see `is_currently_closed`), `PollOption` (ordered by `position`), `Vote` (unique user+poll, final — no changes). List/detail are **public**; create/close are admin-only; results (`votes_count`/`total_votes`) serialize as `null` until visible per F3.3 (voted / closed / requester is admin). List orders open polls first (F3.4) via a `closed_rank` annotation. Gotcha: the options prefetch must restate `.order_by('position')` because `annotate()` drops `Meta.ordering`.

Conventions: `models.py` / `serializers.py` / `api.py` (DRF `@api_view` function-based views) / `urls.py` per app; routing mounted under `/api/users/`, one prefix per card type (`/api/feste/`, `/api/chiese/`, … `/api/itinerari/`), `/api/map/`, `/api/polls/` and `/api/` (reports: `/api/categories/`, `/api/reports/...`) in `backend/backend/urls.py` — `content` is mounted at `/api/content/` for its one endpoint, the counts (see above). UUID pks everywhere. Errors follow `{detail, fields}` via the global handler in `backend/backend/exceptions.py` — raise DRF exceptions, don't hand-roll error JSON. That handler also translates Django's own `ValidationError` into a 400 (TD-14 — the ORM raises it for a malformed UUID and DRF's handler doesn't know it) and rewrites throttle 429s into Italian. Credential endpoints are rate limited via `account/throttling.py` (TD-18); `backend/conftest.py` clears the cache between tests so the limits don't bleed across the suite. Every list endpoint paginates through `common/pagination.py::StandardPagination` (20/page, `page_size` capped at 100); the map payloads (`GET /api/reports/map/`, `/api/map/features/`, `/api/map/overlays/`) and the short admin-managed lookup lists (`/api/categories/`, `/api/luoghi/generi/`, `/api/itinerari/intenti/`) are deliberately unpaginated. `django-debug-toolbar` is a dev dependency and is installed only when `DEBUG and not TESTING` (TD-24).

Auth is JWT (`rest_framework_simplejwt`): global `IsAuthenticated` default, so new endpoints are locked down unless you add `@authentication_classes([])`/`@permission_classes([])` (see `account.api.collaborate`). Hardened in M4: access tokens 60 minutes, refresh 30 days with rotation + blacklist (`token_blacklist` app installed — its migrations must run); the SPA refreshes transparently via the 401 interceptor in `frontend/src/lib/auth.ts` (one retry per request). **Single-flight lives in `stores/user.ts::refreshToken`, not in the interceptor** (2026-08-30): the interceptor is not the only caller — `initStore` refreshes on app start — so a guard inside it could not see that one, and a page load fired two refreshes with the same token. With rotation-and-blacklist on, the second could present a token the first had just invalidated, whose failure path clears the session. `cypress/e2e/session.cy.ts` and two store tests pin it. **A page load refreshes only when the access token is about to expire, and only a 401 ends a session** (2026-09-11, TD-42): `initStore` reads the token's `exp` through `lib/jwt.ts::expiresSoon` — a scheduling decision, not a trust one — because every refresh rotates, and a refresh whose page is torn down is still carried out server-side, so the next load presents a blacklisted token. `performRefresh` keeps the session on a network error or a 5xx, which say nothing about the token; that is why `account/serializers.py::TokenRefreshSerializer` (TD-43) turns a deleted account's refresh into a 401 instead of simplejwt's 500. The accepted cost: after a password change elsewhere, a reloaded tab looks signed in for up to the access token's 60 minutes. Reading CI's `api.log`: on Linux a request whose page died leaves **no line at all**, neither access line nor "Broken pipe" — absence there is not proof. **Logout ends the local session first, then tells the server** (2026-09-11, TD-41): `stores/user.ts::logout` calls `removeToken()` before posting the refresh token, and `/api/users/logout/` takes **no bearer token** (`@authentication_classes([])`) because the request now goes out after the access token is gone — possessing the refresh token is the proof, and blacklisting it ends only that session. The old order waited for the server, so a reload in between kept the session alive and its still-valid access token read a draft after "Esci"; that was `collaborator.cy.ts`'s intermittent failure on main from 2026-09-05. Blacklisting a refresh token never revokes an access token — that is why the local half has to go first. Production serving: whitenoise + `STATIC_ROOT`/`collectstatic`, gunicorn pinned, HTTPS hardening block active when `DJANGO_DEBUG=false` (see docs/deploy.md). Never put `email` into `UserSerializer` — it's intentionally omitted (spec F1.4). `/api/users/me/` is the only place a user sees their own email/role, and it goes through `MeSerializer(UserSerializer)`, which adds exactly those two fields; it used to hand-build a dict and spell the avatar `avatar` instead of `avatarURL` (TD-27). `User.get_avatar()` returns **None** when there is no upload — the SPA renders initials via `components/cards/UserAvatar.vue` (TD-30).

### Frontend (`frontend/`)

Vue 3 + Composition API, Vite, Pinia, Vue Router, Tailwind v4 (+ `@tailwindcss/typography` since C2, for `.prose` on rendered rich text), zod (with Italian locale) for form validation, Leaflet + `leaflet.markercluster` (`components/maps/GaetaMap.vue`, centered on Gaeta; **leaflet is default-imported on purpose** — a namespace import loses the runtime-registered `markerClusterGroup` in production builds; Leaflet is used directly since TD-52 — `@vue-leaflet/vue-leaflet` drew only the map and its tiles, and held the map back for three marker images it fetched itself — and TD-02's `leaflet-src.esm` alias went with it), Tiptap (`@tiptap/vue-3` + `@tiptap/starter-kit`, since C2) for rich-text authoring.

- **C2 content components** (`components/content/`): `RichTextEditor.vue` wraps Tiptap (`StarterKit.configure({ heading: { levels: [2, 3] }, link: {...} })` — StarterKit already bundles Link in Tiptap v3, a separate `@tiptap/extension-link` would just duplicate it); `RichText.vue` is the **only `v-html` in the codebase** (ADR-0001's amendment) — it must only ever render `card.body_html` as returned by the API, never anything else, since its safety argument depends on there being exactly one sanitizing chokepoint (`backend/content/sanitize.py`) feeding exactly one render path. **The map is the other place markup could reach the DOM** (TD-44, 2026-09-18): Leaflet parses a *string* tooltip as HTML, so every text the map shows goes through `lib/mapText.ts::mapText` (a `textContent` node), and `mapText.spec.ts` fails on any `bindTooltip` handed anything else — check any new Leaflet popup, `divIcon` or labelled control the same way. The in-form map editors C2/C3 built — `FesteRouteEditor.vue` and `MapPinsEditor.vue`, on a `composables/useLeafletMap.ts` — **were retired on 2026-09-18** (design.md D19): a card's place is now drawn on the shell's one map, through `components/forms/MapPointsField.vue` (see the map shell bullet). - **C3 generic type components**: `chiese`/`ricette`/`personaggi`/`dialetto`/`libri`/`luoghi` share one config-driven `TypeForm.vue`/`TypeListView.vue`/`TypeDetailView.vue`/`TypeCreateView.vue` set (in `components/content/` and `views/`) instead of four literal copies of the `Feste*.vue` files — each route passes its `definitions/typeConfigs.ts` entry (`endpoint`, `routeNames`, `extraFields`, `mapMode`) as a `config` prop. `feste` keeps its own dedicated views; its route and `recurrence`/`programme` fields don't generalize cleanly and weren't worth disturbing. - **C4 translations** (`components/content/`): `LanguageSwitch.vue` (reader-facing) and `TranslateControl.vue` (the "traduci questo articolo in…" collaborator control, T2) are shared across `TypeDetailView.vue` and `FesteDetailView.vue` — both read the same `translations`/`language`/`translation_of` fields every type's Read serializer now carries, so no per-type copy was needed. `TranslateControl` posts to `<type>/<id>/traduci/`, then `router.push`es straight to the new (empty) translation's own detail route with `?edit=1`; the target-language set is `lib/languages.ts::TRANSLATABLE_LANGUAGES` (English only today, per T1/T3). Both detail views gained a `watch(() => route.params.id, …)` for this: navigating card-detail-to-card-detail keeps the same route record, so Vue Router reuses the component instance instead of remounting it, and `editing` has to drop to `false` before the refetch resolves — `TypeForm.vue`/`FesteForm.vue` only read their `item`/`feste` prop once at setup, so flipping straight to edit mode would otherwise mount the form with the still-stale previous card.

- **C5 the map** (spec map.md): `components/maps/GaetaMap.vue` is the one map — reports (clustered, status colors), the five card layers, and both overlay kinds. It only draws what it is handed: `stores/map.ts` holds which layers are on (since 2026-09-18 — `HomeView`'s toggles write it, `MapStage` passes the filtered `pins`/`features`/`overlays` and the page's `focus`), so the toggles are plain computed filters and not map state. Overlays are added and removed **by id**, never rebuilt as a group, because the opacity slider fires continuously while dragged and a rebuild per tick makes a raster flash; they also get their own Leaflet panes (`z-index` 350/380, between the tiles and everything clickable) so a polygon can't swallow a pin's click. `lib/mapLayers.ts` holds the layer list (key, label, color, route) — `key` is deliberately both the API's `type` and the card's route segment, so a pin knows where it links without a per-type lookup. **The two text lists are the keyboard path a clickable pin does not have, and since 2026-09-05 they are the *decided* conforming path rather than a mitigation while the widget waits** (ADR-0005's map-widget deferral is closed, not outstanding): `PlacesList.vue` for the five card layers, `ReportsList.vue` for the reports layer — which had no list at all until then, so a report was reachable only by clicking its pin. Both render in both homes — `ReportsList` only for someone signed in since 2026-10-22, when the reports layer became a collaborator's alone (`stores/map.ts::loadReports` never asks for reports without an account and forgets them on sign-out, and `visiblePins` is empty for a reader whatever the store holds) — both are filtered by the same `visiblePins`/`visibleFeatures` the map draws, and both carry an `aria-label` ("Luoghi sulla mappa", "Segnalazioni sulla mappa") that the specs select on. **Leaflet markers stay unfocusable on purpose** — `leaflet.markercluster` replaces markers with cluster icons as the reader zooms, so "every marker is in the tab order" is not a state this widget has. That is enforced, not hoped for, since 2026-09-08: `lib/leafletKeyboard.ts` sets `L.Marker.prototype.options.keyboard = false` once (cluster icons are built inside the library on every zoom, so there is no instance to pass an option to), and `a11y.cy.ts` asserts no `.leaflet-marker-icon[tabindex="0"]` survives. Before that the claim was simply false — six unnamed stops announcing as "2", "3", "6". The **container** stays focusable, because that is what arrow-key panning needs, and carries an `aria-label` instead of announcing its own text. If you add a layer to the map, it needs a row in a list too; that is now a rule, not a nicety. `definitions/interfaces/MapData.ts` mirrors the two `maps` endpoints and, like the API, **has no `visibility` field** — do not add one.
- **The map shell** (spec design.md D13/D15/D16/D17, **built 2026-09-18**): **one Leaflet map for the whole app**, `components/maps/MapStage.vue`, mounted by `App.vue` under every route and drawing `stores/map.ts` (features, report pins, overlays, layer toggles, report placing, and the open page's `focus`). **`GaetaMap` is a chunk of its own, and comes after the words** (TD-52, 2026-10-15): `MapStage` fetches the map's data at mount but mounts `GaetaMap` only after the first contentful paint (`lib/firstPaint.ts` — a frame the screen *showed*, not one the main thread painted), and while a page covers the map only once that data is in too. That is also why the home's empty route, `/benvenuto` and `/cosa-fare` are the router's only static views: the reader's ways in paint in the first frame, not a round trip later. Do not import Leaflet, or anything that does, from the entry path — the Lighthouse gate's LCP budget is what it would cost. **Every route but the home renders in `components/layout/RoutePanel.vue`** over it, shaped by `meta.panel` (`'narrow'` for card types with a place and reports, a wide centred panel over a veiled map otherwise; full screen on a phone). **For a card that is its type's default, and the card decides** (2026-10-23, review PR-10; design.md "The card decides its panel"): one with no pin and no route opens wide, with no strip on a phone. The page says so through `composables/usePanelShape.ts` (`cardPanelShape` is the rule), which `App.vue` and `MapStage` both read rather than `meta.panel`; and the five types with a place fetch their card **before** the page mounts (`lib/cardFirst.ts`, a `beforeEnter` that leaves it in `to.meta.card`), so the panel is born in its shape — a page whose card did not come with it asks again itself. **`HomeView.vue` is chrome, not a page**: the home route renders `views/EmptyRoute.vue`, and `App.vue` keeps `HomeView` mounted (`v-show`) for the life of the app so focus can return to the link that opened a panel — it sits *after* the panel in the DOM on purpose (see design.md). The map is `inert` whenever a panel covers it. **The panel closes, it does not go back: close, up, back** (2026-10-23, review PR-22; design.md "Close, up, back"): the close button, Escape and a tap on the veil `router.push('/')` from every page — a tour's stop included — and **no button of the app ever calls `router.back()`**, which `RoutePanel.spec.ts` pins; *up* is a link at the panel's head, one level above, from `lib/navigation.ts::parentOf` (a card → its type's list, `?tappa=N` → its tour, a tour → `/itinerari`, `?zona=` → `/cosa-fare`, a report → `/`; none where the only parent is the map), whose test fails on a route nobody placed; *back* is the browser's, and `?mappa=1`/`?tappa=N` stay steps it undoes. **The up link heads the panel's eyebrow, and the page tells it the rest** (2026-10-23, review PR-23; design.md "Where the reader is"): `RoutePanel` draws a `<nav aria-label="Dove sei">` — up, then what the page is within it — and a page hands over its part through `composables/usePanelTrail.ts`, the way it hands the map a frame: the zones of a card or a festa, each linked to `/cosa-fare?zona=`, a tour's intents, a stop's position with its own tour's name as the way up, a chosen zone. - **The design pass** (spec [design.md](docs/spec/design.md), roadmap item 1, **complete 2026-08-31**): **colour and type live in `assets/main.css` as `@theme static` tokens and nowhere else** (D8) — no component writes a hex or names a font family, and `lib/tokens.ts::readToken` reads them back for the handful of callers that must hand a real colour string to Leaflet, each with the same value as a fallback so a token that fails to cascade degrades visibly rather than to `undefined`. `static` is deliberate: Tailwind otherwise emits only the properties its generated utilities reference, so a token the layout has not reached yet would vanish from the document. **Fonts are self-hosted** (D6b) — a Google Fonts `<link>` would reintroduce exactly what TD-30 and accounts.md A1 removed, and the app ships one `@font-face` with the latin subset rather than `@fontsource`'s three. **`HomeView.vue` is two layouts** (D2/D3/D4), switched in JS at 1024px via `composables/useBreakpoint.ts` rather than with `lg:hidden` on both — only one is ever in the DOM, because two copies mean two `id="layer-chiese"` (and, before the map moved to the shell, two Leaflet maps); `LayerToggles.vue`/`PlacesList.vue` are shared by both, `MapSheet.vue`/`MapChrome.vue` are the small-first pair. `AppHeader.vue` measures itself and publishes `--header-h`, which the shell's padding and the map's height both read — a hard-coded clearance put the map under the header. **The images row is `components/forms/CardImagesField.vue`**, shared by `TypeForm` and `FesteForm` (2026-09-07) — one ordered strip of thumbnails whether an image is already stored or was picked a moment ago, because D5 makes the **first image the cover** and that is an editorial decision, not the order a file picker happened to sort. The same two buttons order a feste's **route stops** (`MapPointsField`), where the order is not editorial but literal — consecutive stops are what the polyline joins — and both call `lib/reorder.ts::moveItem`, which is the only implementation. It is arranged with two buttons per image and no drag-and-drop: dragging cannot be the only way to reorder under ADR-0005, and the labels say where the image goes ("Sposta l'immagine 2 al primo posto: diventa la copertina"). The wire format is `lib/cardImages.ts::appendImages` and `content/api_helpers.py::save_images(card, files, raw_order)`: **`image_order` is a list of tokens** — an existing image's id, or `new:<n>` for the n-th file in *this* request — so a photograph being uploaded now can become the cover in the same save rather than after a round trip. A token nobody recognises is ignored and an image the order does not mention keeps its relative place at the end: a partial order arranges, it does not delete. ## Commands

### Running the whole app (repo root)

```sh
scripts/dev                   # backend :8000 + frontend :5173, bare metal, one Ctrl-C
docker compose up --build -V  # Postgres + backend :8000 + frontend :5173 (-V: TD-51)
```

`scripts/dev` is the fast path: SQLite, `DJANGO_DEBUG=true` exported for you
(TD-11), pending migrations applied first, and it refuses to start when either
port is taken rather than half-starting (`API_PORT=8001 WEB_PORT=5174` moves
them). It kills the whole process tree on exit — `runserver` forks the real
server as its own child and vite runs under npx, so killing only what the
script launched leaves the port held. Use compose when you want Postgres.

### Backend (venv at REPO ROOT: `.venv`)

```sh
python3 -m venv .venv && source .venv/bin/activate    # first time
python -m pip install -r backend/requirements-dev.txt # runtime + pytest/ruff

cd backend
export DJANGO_DEBUG=true                              # once per shell (see below)
python manage.py migrate
python manage.py runserver                            # http://127.0.0.1:8000

python -m pytest                                      # canonical test runner
python -m pytest account/tests.py -k collaborate           # subset
python -m ruff check .                                # lint (must be clean)
```

`python manage.py test` exits 0 but runs nothing (tests are pytest-style) — use pytest.
Shared fixtures (`api_client`, `citizen`, `other_citizen`, `admin`, `make_client`,
autouse `media_root` and a throttle-cache reset) live in `backend/conftest.py`;
`PASSWORD` is in `common/testing.py`. Under pytest, `settings.py` swaps in the MD5
password hasher (TD-05) — that is why the suite runs in ~3s rather than ~50s.

**`DJANGO_DEBUG` defaults to false (TD-11).** Forgetting the variable fails safe
instead of serving tracebacks, and outside debug/test the app raises
`ImproperlyConfigured` unless `DJANGO_SECRET_KEY` is set — it is SimpleJWT's
signing key, so a committed fallback meant anyone could mint an admin token.
Development opts in: `docker compose` passes `DJANGO_DEBUG=true`, bare-metal
shells `export` it, and pytest is exempt via the `TESTING` flag (which is also
why the HTTPS hardening block carries `and not TESTING` — without it
`SECURE_SSL_REDIRECT` answers the test client with a 301).

**To see the archive full while it is empty**, `python manage.py seed_demo`
(DEBUG only, spec cosa-fare.md Part −1 D8) publishes seventeen invented cards
titled `[DEMO] …` across the eight zones — places, churches with sample
hours, a festa, two ricette, two tours — and no images, on purpose;
`seed_demo --remove` takes away exactly those. They are not content: real
cards are written in the app, under content.md's rules for writing from
published sources. **There is no other seeding command, on purpose**: the
public-source drafts and `seed_drafts` (2026-10-14) were **removed on
2026-10-22** — the author judged them a trial, not material to publish, so
production was born empty and stays so until someone writes in it. Do not
bring a seeding command back for production content.

Create a superuser via `python manage.py shell`:

```python
from account.models import User
User.objects.create_superuser(email="admin@example.com", password="password123", name="admin")
```

### CI

`.github/workflows/ci.yml` runs the gates on every push to `main` and every pull
request: backend (ruff + pytest, Python 3.14, SQLite fallback) and frontend
(oxlint + eslint + prettier `--check` + vitest + build, Node 22). A third job runs
Cypress against a **production build** (`npm run test:e2e`, vite preview on
:4173) — not the dev server, because TD-02's double Leaflet bundle and the
default-import gotcha only appear in built output. It must stay green. Two
things to know before editing it: the linters run **check-only** there, because
`npm run lint` applies `--fix` and would let CI pass by rewriting files; and the
e2e job **starts a real Django API on :8000** (TD-04, 2026-08-30) seeded by
`python manage.py seed_e2e` — a DEBUG-only management command, since it creates
accounts whose password is written down in a spec file — and, since
2026-09-04, **clears what the v1 flows leave behind**: a vote is final by
design (F3.2) and an upvote is a toggle, so a suite re-run against a database
nobody re-seeded fails on the app behaving correctly. Re-seed between runs; the
first assertion to go red is the poll's "results are hidden before you vote".
The SPA's API base URL
defaults to `http://127.0.0.1:8000`, which is why the build needs no extra
environment there; it would if the API ever moved. **Running the e2e suite
locally needs the same API *and* `CORS_ALLOWED_ORIGINS` pointed at the preview
origin** — the default is `:5173`, so without it every request from `:4173` is
blocked by the browser while the server cheerfully logs a 200, and the specs
fail as if the data were missing:

```sh
cd backend && export DJANGO_DEBUG=true E2E_MAIL_DIR=/tmp/vivere-gaeta-mail \
  CORS_ALLOWED_ORIGINS='http://localhost:4173,http://127.0.0.1:4173'
python manage.py seed_e2e && python manage.py runserver 127.0.0.1:8000 --noreload
# then, from frontend/, after a build:
#   E2E_MAIL_DIR=/tmp/vivere-gaeta-mail npm run test:e2e
```

`export`, not a prefix, and it matters: `VAR=x a && b` gives the variables to
`a` only, so the command this block used to print started `runserver` with
neither DEBUG nor the preview origin — the very failure the paragraph above
warns about (found 2026-09-10). **`E2E_MAIL_DIR` must name the same directory
for the API and for Cypress**: the API writes its mail there as files (DEBUG
only, a branch production cannot reach) and the `inviteLink` task in
`cypress.config.ts` reads the invite back, so `collabora.cy.ts` can follow a
request through the author's approval in Django admin to a collaborator who
signs in. `seed_e2e` makes its admin a Django superuser for that reason, and
clears every `@e2e.test` request and `invito-…` account a previous run left.

**The WCAG 2.1 AA gate lives in that same job** (`cypress/e2e/a11y.cy.ts`,
2026-08-31): axe-core through `cypress-axe`, ADR-0005's four WCAG tags and no
`best-practice` rules, over twenty cases — *Il progetto*, the welcome page, a tour, the tour form and the form drawing on the map joined on 2026-09-18, *Cosa si può fare qui* on 2026-10-13, the collaborator's home with its reports on 2026-10-22 (they left the reader's home that day), `/luoghi` without covers in both layouts on 2026-10-23 (on `seed_e2e`'s Serapo beach), a toast over a panel in both layouts the same day (review PR-8), *Password dimenticata*, the login on a phone and the profile's two forms the same day too (review PR-11) — (plus four cases that are about the keyboard rather than axe: the skip link, the map's pins staying out of the tab order, *Cosa si può fare qui*'s zone links, and the login answering Enter in a field) including an authoring form
*showing a real validation error* and the same form *with images attached* (the
images strip does not exist until it has images, so nothing measured it before). Three things it will teach you the hard way if
you extend it: it excludes `.leaflet-container`, which since 2026-09-05 is ADR-0005's *decision* (the text lists are
the conforming path) rather than a deferral; it waits for the wordmark's fade-in to finish before
measuring, because axe samples whatever colour the compositor is showing and
mid-animation that is a real reading of a meaningless value; and **it blends the map's tiles normally before
measuring** (`blendTilesNormally`, 2026-10-23, review PR-8) — Leaflet's tiles carry `mix-blend-mode: plus-lighter`,
axe-core has no formula for it, and `color-contrast` threw, filed itself as "incomplete" and skipped every page
over the map while cypress-axe stayed green. A case of its own (*measures contrast*) fails if the rule throws
again or judges no text, so call `check()`, not `cy.checkA11y` bare, in a new case. A green run is a
floor, not a conformance claim: while the auth forms' labels were unassociated
the gate passed them anyway, because an input takes an accessible name from its
`placeholder` — ADR-0005 is what got them fixed, not a red build. **Watch the login
count when adding specs:** the endpoint is rate limited to 10/min per IP
(TD-18) and a whole run spends eight of those (the invite journey in `collabora.cy.ts` signs its new collaborator in once), so a new suite that signs in per test
turns the whole run intermittently red with a 429 the SPA reports as a wrong
password. The a11y spec's collaborator block uses `testIsolation: false` and
one `before` login for that reason. **`cy.session` is not the answer here**:
refresh rotation with a blacklist means a cached snapshot replays a token the
previous test already spent, and the app correctly logs itself out — tried,
and it fails as 401s on every write.

**The lint policy is pinned, in both languages, and that is deliberate** (TD-33, 2026-09-05). `backend/pyproject.toml` selects ruff's rules explicitly (`select = ["E4", "E7", "E9", "F"]` — 0.15's defaults, written down) because with `select` implicit a version bump redefines what "clean" means: 0.16 would have arrived with 81 findings on unchanged code. `frontend/.oxlintrc.json` still selects the `correctness` *category* — new correctness rules are closer to bug reports than to opinions, and pinning rule ids there would be unmaintainable — but its `overrides` now scope the **vitest** plugin to `src/**/__tests__/**`, because applied repo-wide it reads the Cypress specs and reports every Chai `expect(x).to.equal(y)` as an "unknown modifier". Widening either set is a separate PR from bumping either tool: a lint sweep has an opinion in it, and a bump should not. **`axe-core` belongs to the same policy** (2026-10-12): it is the a11y gate's rule engine, so a minor bump can turn the gate red on unchanged code — 4.14 began enforcing WCAG 2.5.3 (label in name) on the editor toolbar and the account button, and it drops a parenthetical from a name before comparing, and counts `aria-hidden` text as visible. Bump it on its own or expect to fix what it finds. And in the a11y spec's collaborator block (`testIsolation: false`), **a failure early on can surface later as a `settle()` timeout** on an unrelated page — the wordmark's fade read 0.29 opacity on `/users` in CI until the earlier failure was fixed; fix the first red case before chasing the others.

**The performance gate is a fourth job, `lighthouse`** (2026-10-15): Lighthouse CI on a production build against the same seeded API, configured in `frontend/lighthouserc.yml` — `/benvenuto`, `/` and `/cosa-fare` on Lighthouse's simulated phone, three runs each, the median asserted. CLS ≤ 0.1 and **LCP ≤ 2.5 s are web.dev's "good"** — LCP since TD-52 was paid (2026-10-15; medians 1.76–1.94 s in a Linux container under `act`, 1.84–1.85 s on a Mac); **TBT ≤ 300 ms is a regression budget, not "good"** (TBT stands in for INP, which a lab cannot measure) — it scales with the runner's CPU and with whatever else that machine is running: medians 84–206 ms under `act`, 5–14 ms on a Mac, and one `act` run on a heavily loaded machine failed at 552 ms (`lighthouserc.yml` says what that task is). Never raise a budget to make a run green. Three things it does on purpose: it **blocks OpenStreetMap's tiles**, because the tile policy forbids headless bots — so the LCP it measures is the app's own text, and what a tile adds is in TD-52's archive entry; it runs `@lhci/cli` through a pinned `npx` rather than a devDependency (~3,400 lockfile lines and 17 npm-audit advisories for a tool nothing ships); and it never uses LHCI's temporary public storage — the reports are the `lighthouse-reports` artifact, uploaded green or red. Locally, from `frontend/` after a build and with the API on :8000 allowing `http://127.0.0.1:4173`: `npx @lhci/cli@0.15.1 autorun`. Under `act` the runner image needs a Chromium (act's has none, and Google Chrome has no linux/arm64 build — Playwright's Chromium works) and `CHROME_PATH` pointing at it.

**The Cypress suite never fetches a tile either**, for the same policy (2026-10-15): a `beforeEach` in `cypress/support/e2e.ts` answers every request to `OSM_TILE_URL` with `cypress/fixtures/tile.png`, a transparent 1×1 PNG Leaflet counts as loaded, and `blockHosts: ['*.openstreetmap.org']` in `cypress.config.ts` is what holds where no intercept is registered — a describe-level `before()` runs after intercepts are cleared and ahead of every `beforeEach`, and `a11y.cy.ts`'s collaborator sign-in alone sent 30 tile requests out before it was there.

Two upgrades are **held back on purpose**, with the reasons in TD-06 rather than in a lockfile nobody reads: **cypress 16** (`cypress-axe@1.7.0` peers only up to 15, so the a11y gate's plugin would go to an invalid peer state — and 16 counts a `.sr-only` element as visible, which `login.cy.ts` asserts against) and **typescript 7** (`vue-tsc` cannot load it: `ERR_PACKAGE_PATH_NOT_EXPORTED`).

Definition of done for a feature (spec §9): the spec section it implements is referenced, pytest + Vitest green, ruff + eslint + prettier (`--check`) clean, `npm run build` green. CI runs all of it on every push and pull request.

## External agent skills (agent-skills + impeccable)

Two third-party skill packs are used with this repo, installed as **Claude Code
plugins (never vendored)** so nothing of theirs is committed here:
[addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) (engineering
process: spec → plan → build → test → review → ship) and
[pbakaus/impeccable](https://github.com/pbakaus/impeccable) (frontend design
quality; 59 deterministic detector rules, `.vue` supported). They do not conflict
with each other — one covers process, the other aesthetics — but they do carry
their own conventions, which this project overrides as follows.

**Install scopes** (2026-08-19). agent-skills is installed at **`local` scope,
pinned to this repo** — declared in `.claude/settings.local.json`, which
this repo's `.gitignore` excludes, so the marketplace reference stays out of the
public repo on every clone and the pack loads in no other project. (Until
2026-08-19 it was covered only by a machine-level `~/.config/git/ignore`, so the
guarantee did not travel — DOC-04.)

impeccable stays a **`user`-scope** install and is currently *disabled*; enable it per session when you actually want a design
pass. Manage both with `claude plugin ... --scope local` from the repo root;
`claude plugin list` shows what is active. Plugins load at process start, so a
scope change only takes effect in the next session.

**Precedence.** The project workflow wins. agent-skills injects a routing
meta-skill at every session start whose behaviours are phrased as
"non-negotiable"; where it disagrees with [docs/mvp-spec.md](docs/mvp-spec.md) §10
(spec first, one goal per session, session log, human ownership) or with the
commands above, this file is authoritative.

**Where artifacts go.** agent-skills defaults to writing `tasks/plan.md` and
`tasks/todo.md` at the repo root — **don't**. `docs/mvp-spec.md` is the scope
authority, planned work goes in [docs/roadmap.md](docs/roadmap.md), debt in
[docs/tech-debt.md](docs/tech-debt.md) (paid debt in
[docs/tech-debt-archive.md](docs/tech-debt-archive.md)), and
expensive-to-reverse decisions in
[docs/adr/](docs/adr/README.md). Per-task planning files are churn: this repo
has no session logs, by decision (2026-08-20).

**Definition of done** stays the project's own (spec §9): pytest + ruff + Vitest
+ eslint + prettier `--check` + `npm run build`. A skill's generic checklist does not replace it.

**Language.** Both packs write English by default; UI copy in this app is Italian
(N4). Any copy a skill proposes for the SPA must be translated before it lands.

**Scope guard — lifted 2026-08-22.** `/impeccable audit` and agent-skills'
`frontend-ui-engineering` both push for a full WCAG pass. That used to be
advisory here, because v1's N5 had scoped it out and the question was still
open. It is **decided now**: WCAG 2.1 AA, whole app
([ADR-0005](docs/adr/0005-wcag-2.1-aa-accessibility-bar.md)), so their contrast
and keyboard findings land against a bar this project has accepted — check them
against the ADR's Consequences, which says what is already fixed and what is
deliberately deferred, rather than dismissing them as out of scope.

**Adopted from the pack:** `documentation-and-adrs` — its README structure
(name, one-paragraph description, Quick Start, Commands, Architecture) and its
ADR format and rules on when one is worth writing. See `docs/adr/README.md`.

**Skills not to use here.** Enabling the pack loads all 24 skills, so the
exclusions are rules rather than missing files:

- `spec-driven-development` and `planning-and-task-breakdown` — **evaluated
  2026-08-20 and not adopted**, deliberately, as this file's own rule required.
  The reason is worth keeping: the six areas of the pack's spec template are
  Objective, Commands, Project Structure, Code Style, Testing Strategy and
  Boundaries — five of which are *this file*. It overlaps CLAUDE.md, not
  `docs/mvp-spec.md`, and it has no equivalent of a product spec (F1/F2/F3,
  non-goals). It also mandates `tasks/plan.md` + `tasks/todo.md` per task. So:
  `docs/mvp-spec.md` stays the product spec, CLAUDE.md stays the working
  agreement. Do not run both systems. (Same call the author made in the
  `next-cmp-settings` project, for the same reason.)
- `browser-testing-with-devtools` — requires the `chrome-devtools` MCP server,
  which this setup does not have; use the built-in browser preview instead.
- `performance-optimization` — premature here. Measure after the demo is live
  and only against a real complaint.

**impeccable specifics.** `.impeccable/` is gitignored (live-mode config + cache).
`/impeccable live` temporarily injects a script into `frontend/index.html` —
never commit that inject. If `/impeccable init` writes a root `PRODUCT.md`, it
carries design-facing context only; product scope stays in the spec.
Detector baseline at setup time (2026-08-19), **one real finding, one false
positive** (re-checked in the 2026-08-19 deep audit):

- Real, and **since acted on**: `SiteTitle.vue` used a purple gradient, flagged
  as the classic "AI-generated UI" tell. It was the M4 brand, so it was left as
  a product call rather than a defect — and the design pass took that call in
  2026-08-31's palette (design.md D6/D8). The gradient is gone, the component
  lives at `components/typography/SiteTitle.vue`, and its file says so. Kept
  here because the *reasoning* is the pattern: a detector finding on a brand
  asset is a product decision, not a lint failure.
- **False positive:** the reported `text-gray-600` on `bg-green-100` in
  `PollCard.vue:91` does not exist. That line is a ternary and the pairs that
  actually render are `bg-gray-200 text-gray-600` and `bg-green-100
  text-green-700`; the detector combined classes across the `?:`. Do not spend a
  session on it, and treat ternary class bindings as a known blind spot of the
  contrast rule.
