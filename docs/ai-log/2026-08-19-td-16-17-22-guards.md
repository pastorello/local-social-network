## 3. What the AI produced

**TD-16 — two strings, but the point was running it.** The spec asserted

I ran Cypress **before** touching anything: 3 tests, 2 passing, **1 failing** —

**TD-17 and TD-22 — the code was already right.** These are unpinned
invariants, not bugs, so the tests pass on the first run. That makes them
worthless unless they can fail, so each was mutation-tested:

| Mutation | Result |
|---|---|
| add `'role'` to `SignupForm.Meta.fields` and `ProfileForm.Meta.fields` | both TD-17 tests fail |
| drop `.order_by('position')` from `polls/api.py:35` | the TD-22 test fails — and the **six** pre-existing ordering assertions all still pass |

That last line is the finding restated as evidence: every other fixture inserts
options in ascending position, so without any `ORDER BY` the database returns
insertion order, which *is* position order. The new test inserts them backwards.

**Cypress joined CI** as a third job. It runs against a **production build**
(`npm run test:e2e`, vite preview on :4173) rather than the dev server — TD-02's
double Leaflet bundle and the default-import gotcha only appear in built output,
so a dev-server run would miss the bug the suite exists to catch. The binary is
cached on `package-lock.json`; a failed run uploads screenshots and videos. No
backend service, because today's specs exercise the SPA shell only — recorded in
the job so the next spec author knows to add one.
