## 2. Plan prompt

> ora facciamo TD-01, la CI

**Plan accepted / amended:** implemented as the register specifies — one
workflow, two jobs, no deploy step. Three additions the register did not
anticipate, each forced by something measured in the repo rather than assumed:

- **The linters cannot be run through `npm run lint`.** That script is
  `oxlint . --fix` then `eslint . --fix --cache`. In CI `--fix` would let a run
  pass by rewriting files in the runner. The workflow calls `npx oxlint .` and
  `npx eslint .` instead — verified locally that both are clean without `--fix`,
  so this does not turn CI red on day one.
- **`npm run test:unit` is watch mode.** It is `vitest`, not `vitest run`; the
  workflow uses `npm run test:unit -- run`. (This is also the half of DOC-06
  that complained the README's `&&` chain never reaches `lint`/`build`.)
- **`npm ci` triggers `cypress install` via the `prepare` script.** No job here
  runs Cypress, so the step sets `CYPRESS_INSTALL_BINARY=0` to skip a large
  download on every run.

## 3. What the AI produced

**`.github/workflows/ci.yml`** — two jobs on push-to-`main` and every pull
request, with `concurrency` cancelling superseded runs and `permissions:
contents: read`.

- **backend:** Python **3.14** (matches `backend/Dockerfile`), pip cache keyed on
  `requirements-dev.txt`, then `ruff check .` before `pytest` so style fails
  fast. No `POSTGRES_HOST`, so `settings.py` falls back to SQLite.
- **frontend:** Node **22**, npm cache keyed on `package-lock.json`, then oxlint,
  eslint, vitest, and `npm run build` (which is `run-p type-check build-only`, so
  `vue-tsc` runs there).

**Three deliberate omissions, documented in the workflow header** so the next
session does not read them as oversights: no deploy step (roadmap item 2 is
parked); **no Cypress job** — `login.cy.ts` has been red since M4 (TD-16), so
wiring it in now would mean a permanently failing CI, and the register orders
TD-16 before any e2e work; no Postgres service — the suite runs on the SQLite
fallback, which is what every developer runs locally, and testing against
Postgres too is a later decision rather than an omission.

**One correction to the register's own text.** TD-01 specified "Node 24". 24 is
the dev machine; `frontend/Dockerfile` is `node:22-alpine` and `package.json`
engines allow `^20.19.0 || >=22.12.0`. CI now matches the image that would
actually ship. The 22-vs-24 drift between the Dockerfile and the dev machine is
real and worth unifying, but it is not this session's scope.
