# ADR-0005: Vivere Gaeta commits to WCAG 2.1 Level AA

## Status

Accepted

## Date

2026-08-22

## Context

v1 scoped accessibility out entirely (spec N5, recorded at MVP time): the
product was a civic tool for a known, local audience, and WCAG conformance was
deferred rather than decided against. The v2 recentering to a curated cultural
archive **aimed at tourists** — an audience of strangers on unknown devices,
some of whom will be assistive-technology users — raised the stakes enough
that [docs/roadmap.md](../roadmap.md) reopened the question at C2 and asked
that it be answered "before C3 adds four more templates on the same pattern."

It was not answered during C2 itself — that phase shipped reasonable defaults
(real `alt` text on card images, semantic tags via the rich-text sanitizer
allowlist) but no recorded bar and no audit. This ADR is that overdue
decision, made explicitly rather than by drift.

## Decision

Vivere Gaeta targets **WCAG 2.1 Level AA**, across the **whole application** —
not only new card templates (C2 onward) but the v1 surfaces already shipped
(reports, polls, account/auth screens). Scoping it to "new work only" was
considered and rejected: a reader does not experience `reports` and `feste` as
different products, and a partial bar is not a bar a screen-reader user can
rely on anywhere in the app.

This is a **target with a remediation plan**, not a claim of present
conformance. Nothing in the codebase has been certified against WCAG 2.1 AA as
of this ADR's date; see Consequences for what that implies about sequencing.

## Alternatives considered

**Bar scoped to new card templates only** (the option the roadmap's own
framing implied). Cheaper and immediately achievable, but leaves `reports` and
`polls` — both already public, already used by anonymous visitors — outside
the bar indefinitely, with no forcing function to ever revisit them.

**Stay out of scope until near public launch** (reconfirming v1's N5).
Consistent with "deployment is last, on the author's signal" and defers cost
to when it's cheapest to also do a full audit in one pass — but the author
explicitly chose the stricter bar now, over this option, when asked.

**Automated tooling first** (enable the `impeccable` plugin's WCAG-adjacent
checks, or wire `axe-core` into the Cypress suite, before any manual work).
Rejected as the *starting* move, not as a later step: `impeccable` is
user-scope-installed but disabled, and CLAUDE.md records that a plugin scope
change only takes effect in the next session — it cannot be turned on
mid-session. `browser-testing-with-devtools` (chrome-devtools MCP) is also
unavailable per CLAUDE.md. The first audit pass is therefore manual/heuristic
(code review + browser spot-checks); automated regression tooling is
Consequence, not a prerequisite.

## Consequences

- **A first remediation pass landed with this ADR**, driven by a static-analysis
  audit (code review, no browser automation tooling available — see
  Alternatives) covering every view and component. Fixed: the `<label>` with
  no `for`/`id` pattern copied across every form since M1 (now paired
  everywhere, including search inputs and the poll/report/feste forms);
  icon-only controls with no accessible name (nav icons, the rich-text
  toolbar, route/image remove buttons — now `aria-hidden` where decorative,
  `aria-label`/`aria-pressed` where interactive); two `<h1>`s per page
  (`SiteTitle.vue`'s wordmark was a heading, duplicating each view's own
  `MainTitle` — now a plain link; `ProfileView.vue` conversely had none — now
  has one); color-contrast failures against the actual Tailwind values in use
  (`StatusBadge.vue`'s status colors, the error-message boxes on every form,
  `ActionButton`'s success variant — all previously under 4.5:1, computed via
  the WCAG relative-luminance formula, now at or above it); and the two
  Critical keyboard-only interactions with no alternative (`HomeView.vue`'s
  report-location picker and `FesteRouteEditor.vue`'s stop picker both
  required a mouse click on the Leaflet map — both now also accept manual
  lat/lng entry).
- **Deferred, not silently dropped**: full screen-reader operability of the
  Leaflet map widgets themselves (marker hover tooltips have no keyboard-focus
  equivalent — an inherent limitation of tile-based map libraries, mitigated
  today by both maps also exposing their data as text lists, not fixed at the
  widget level); `aria-describedby`/`aria-invalid` wiring so a validation
  error is associated with the field that caused it, not just listed
  generically at the form's end; file-input constraint text (size/format)
  exposed only in visible label copy, not `aria-describedby`; a systematic
  focus-order and skip-link pass. WCAG 2.1's touch-target-size criterion
  (2.5.5) is **Level AAA, not AA** — the bar this ADR commits to — so the
  several sub-44px icon buttons in the audit are noted but intentionally not
  treated as blocking.
- **Update, 2026-08-30 (design pass):** two of the deferred items above are
  closed on the authoring screens — the ones where a validation error actually
  happens. `components/forms/FormField.vue` now owns the label/control/error
  relationship in one place, so `aria-describedby` and `aria-invalid` cannot be
  half-wired: a rejected field points at its own message and announces itself
  invalid, instead of the message sitting alone at the foot of the form. The
  file-input constraint text (size and formats) is exposed through the same
  mechanism rather than in visible copy only. Verified against a real 400 from
  the API, not only in unit tests. Still deferred, unchanged: the map widgets'
  own operability and the focus-order and skip-link pass. The same wiring has
  *not* yet been applied to the auth and profile forms, which still use the
  older `<label>…</label><br />` pattern.
- **Update, 2026-08-31: the auth and profile forms have it too**, which closes
  the error-to-field item outright. `LoginView`, `CollaboraView`,
  `InviteAcceptView`, both password-reset views, `EditProfileView` and
  `EditPasswordView` moved onto `FormField`, so a rejected box announces
  itself and carries its own message. Three things came with it, because they
  are one defect seen from three sides:

  - **Validation is attributed, not prefixed.** `parseZodObject` returns
    `fieldErrors` keyed by the field that failed, and the label it used to glue
    to the front of each message ("E-mail: …") is gone — under its own label,
    the prefix repeats what a screen reader has just announced.
  - **API errors are kept per field** (`extractFieldErrors`), so Django's own
    password validators land under the box they are about. What genuinely has
    no field — login's deliberately vague "e-mail o password non corretti",
    which must not say *which* of the two was wrong — stays form-level, in one
    `FormErrors` component with `role="alert"`.
  - **That box failed contrast on the login form**: white on `bg-red-300`,
    1.9:1. The gate could not have caught it, because it only appears after a
    failed sign-in — which is the argument for the gate carrying an error-state
    case per form, and it now carries two.
- ~~**No CI gate exists yet.**~~ **Built 2026-08-31**, and it is the
  obligation this paragraph created: `frontend/cypress/e2e/a11y.cy.ts` runs
  axe-core (via `cypress-axe`) over eleven surfaces — the map home at both
  widths, a card list, a card as an article, the public request form, login,
  the polls, the user directory, a profile, the authoring form, and two forms
  *showing a real validation error* — login and authoring — which is where
  label, message and control either stay wired together or do not. It runs in the existing e2e
  job, so it gates every push and pull request against the production build.

  Three things it deliberately is not:

  - **Not a conformance certificate.** Automated rules catch a minority of WCAG
    failures. Green means no machine-detectable violation of `wcag2a`,
    `wcag2aa`, `wcag21a` and `wcag21aa` — a floor under manual review, not a
    replacement for it. The worked example is the auth forms: while their
    `<label>` elements were unassociated the gate passed them anyway, because
    an input takes an accessible name from its `placeholder`. What fixed them,
    on 2026-08-31, was this ADR — not a red build.
  - **Not a check of the map widget.** `.leaflet-container` is excluded, which
    is exactly the deferral recorded above rather than a new one. One selector,
    so the day the widget is addressed, deleting the line is the whole change.
  - **Not `best-practice`.** Only the four WCAG tags above run. The
    best-practice rules are opinions this project has not adopted, and failing
    on them would make the gate an argument rather than a check.

  One finding from building it, worth keeping: axe samples the colours the
  compositor is showing *at that instant*, so the wordmark's 800 ms fade-in
  read as a 1.94:1 contrast failure for text that settles at 14.76:1. The spec
  waits for the animation to finish before measuring — a gate that judges a
  frame of a page's entrance rather than the page reports things nobody can
  act on.
- **C3's four remaining card types inherit this bar from day one** — the
  point of deciding now rather than after C3, per the roadmap's own framing.
